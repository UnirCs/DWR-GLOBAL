01

¿Qué es SASS?

SASS (Syntactically Awesome Stylesheets) es un preprocesador CSS: una herramienta que extiende la sintaxis del CSS permitiendo usar funcionalidades propias de lenguajes de programación. Escribes .scss, y SASS lo compila a CSS plano que el navegador entiende.

📝

Escribes SCSS

Código con variables, anidación y lógica. Más expresivo que el CSS.

⚙️

SASS compila

El preprocesador traduce todo a CSS estándar, optimizado.

🌐

El navegador lee CSS

El resultado es CSS normal: el navegador nunca ve tu SCSS.

Otros preprocesadores del mismo ecosistema: Less, Stylus y PostCSS. SASS es el más extendido.

03·a

A mano (HTML y CSS puro)

Este flujo aplica cuando no usas un bundler ni un framework: un proyecto de HTML + CSS sin más. Como no hay nada que dispare la compilación, eres tú quien arranca el compilador. El navegador no entiende SCSS: solo lee CSS. Por eso necesitas un paso de compilación que traduzca tus .scss a .css. Aquí tienes exactamente qué hace el desarrollador a mano y qué hace la herramienta sola, paso a paso, desde la terminal en la raíz del proyecto.

1
✋ manual · terminal

Instalar SASS

En la raíz del proyecto (donde está tu package.json), instala el compilador como dependencia de desarrollo:

# si aún no tienes package.json: npm init -y # instalar el compilador SASS: npm install -D sass

El flag -D lo guarda en devDependencies: solo se usa al desarrollar, no se envía al navegador.

2
✋ manual · crear carpetas y archivos

Crear la carpeta de fuentes y tu primer .scss

Crea tú mismo una carpeta para el código fuente (convención: scss/ o styles/) y dentro un archivo de entrada scss/main.scss. La carpeta de salida css/ la generará la herramienta sola en el paso 3 — no la creas tú.

# crear la carpeta de código fuente a mano: mkdir scss # crear el archivo de entrada (con tu editor o así): echo '$color: #cf649a; body { color: $color; }' > scss/main.scss
3
⚙️ automático · lo hace SASS

Arrancar el compilador en modo --watch

Este comando deja a SASS vigilando la carpeta de entrada. Cada vez que tú guardes un .scss, él recompila y escribe el .css automáticamente. Déjalo corriendo mientras trabajas.

# formato: sass --watch [entrada]:[salida] npx sass --watch scss:css

SASS crea solo la carpeta css/ y dentro main.css (+ un main.css.map para depurar). Nunca edites el CSS generado: tus cambios van siempre en los .scss.

4
✋ manual · en tu HTML

Enlazar el .css compilado (no el SCSS)

En tu HTML enlazas el archivo de salida que generó SASS, no el .scss. El navegador solo ve CSS:

<!-- index.html --> <link rel="stylesheet" href="css/main.css">
5
✋ recomendado · package.json

Guardar el comando como script

Para no recordar la ruta cada vez, añade tú un script en package.json. Luego arrancas con npm run sass:

// package.json "scripts": { "sass": "sass --watch scss:css", "build:css": "sass scss:css --style compressed" }
Regla de oro: tú editas archivos .scss → SASS los compila → el navegador lee el .css resultante. El .css es un artefacto generado; muchos equipos lo añaden a .gitignore y lo regeneran en cada build.

Tipos de archivo que vas a manejar

.scss

Lo que tú escribes. Sintaxis con llaves y ; (parecida a CSS). Es la que usa todo el mundo hoy.

_archivo.scss

Un parcial: el guion bajo le dice a SASS que no genere un .css propio. Se importa desde otros. Tú creas estos.

main.scss

El punto de entrada (sin guion bajo). Importa todos los parciales. Es el único que se compila a un .css final.

.sass

Sintaxis antigua, por indentación y sin llaves ni ;. Existe pero casi nadie la usa; quédate con .scss.

main.css

Generado por SASS, no lo tocas. Es lo que enlaza el navegador.

main.css.map

Generado. Un source map que conecta el CSS con tu SCSS para depurar en DevTools.

03·b

Con framework (Next.js)

Cuando usas un bundler o framework (Next.js, Vite, Angular…), no necesitas el comando --watch: el propio framework detecta y compila SASS durante el desarrollo y el build. Instalar sass y crear archivos .scss es suficiente — por eso quizá no recuerdes haber lanzado nunca el compilador a mano. Tu único paso manual extra es instalar el paquete. Elige el patrón según cómo quieras aplicar los estilos.

Paso manual único: instalar sass

Desde la raíz del proyecto Next.js. No hay que configurar nada más en next.config.js: Next lo detecta automáticamente.

npm install -D sass

A partir de aquí, ejecutas tu proyecto como siempre (npm run dev) y Next compila el SASS al vuelo.

Estilos globales

Tú creas un archivo, p. ej. app/globals.scss, y lo importas una sola vez en el layout raíz. Solo el archivo global puede importarse así.

// app/globals.scss (lo creas tú) $marca: #cf649a; body { margin: 0; color: $marca; }
// app/layout.tsx import './globals.scss'; export default function RootLayout({ children }) { return <html><body>{children}</body></html>; }

CSS Modules con SCSS (recomendado por componente)

El archivo debe llamarse algo.module.scss. Next aísla las clases por componente (sin colisiones de nombres). Tú creas el .module.scss y lo importas como objeto.

// components/Boton.module.scss (lo creas tú) $radio: 8px; .boton { background: #cf649a; border-radius: $radio; &:hover { opacity: .9; } }
// components/Boton.tsx import styles from './Boton.module.scss'; export default function Boton() { return <button className={styles.boton}>Click</button>; }

Compartir variables y mixins entre archivos

Crea tú una carpeta styles/ con parciales (_variables.scss, _mixins.scss) y úsalos con @use. Opcionalmente, registra esa carpeta en next.config.js para importar sin rutas largas.

// next.config.js (edición manual opcional) const path = require('path'); module.exports = { sassOptions: { includePaths: [path.join(__dirname, 'styles')], }, };
// dentro de cualquier .scss o .module.scss @use 'variables' as v; .tarjeta { color: v.$marca; }
Diferencia clave con el proyecto "a mano": en Next.js no arrancas sass --watch ni enlazas un .css en el HTML. Importas el .scss directamente en tu componente/layout y el framework se encarga de compilar y de inyectar los estilos. Tu trabajo manual se reduce a: instalar el paquete + crear y nombrar bien tus archivos.

Funciones & Bucles

08

Estructurar los archivos

Los archivos que empiezan con _ son parciales: no se compilan solos, se importan desde un main.scss. Esta es la estructura recomendada (patrón 7-1 simplificado).

/scss base/ _reset.scss _variables.scss _mixins.scss layout/ _header.scss _footer.scss components/ _boton.scss _tarjeta.scss pages/ _home.scss main.scss ← punto de entrada

10

Más cosas que puedes hacer

SASS da para mucho más que variables y anidamiento. Aquí tienes tres recetas reales explicadas paso a paso — todas compilables en vivo. Edita el SCSS y observa el CSS que genera.

1 · Mapas + @each — generar clases en serie

Sirve para crear muchas clases parecidas (utilidades de color, espaciado, etc.) sin escribirlas una a una.

  1. Defines un mapa $colores: una lista de pares "clave": valor, como un diccionario.
  2. @each $nombre, $valor in $colores recorre el mapa y, en cada vuelta, $nombre y $valor toman los datos de una entrada.
  3. #{$nombre} es interpolación: inserta el valor de la variable dentro del nombre del selector (.bg-#{$nombre} → .bg-primario).
  4. SASS repite el bloque por cada entrada → 4 colores producen 8 clases de CSS. Añade un color al mapa y verás aparecer sus dos clases solas.

2 · Funciones de color — variaciones automáticas

Sirve para derivar bordes, sombras o estados :hover a partir de un único color base, sin elegir cada tono a mano.

  1. @use "sass:color" carga el módulo de color de SASS, que trae funciones para manipular colores.
  2. Defines un solo color base en $base.
  3. color.adjust($base, $lightness: -18%) devuelve el mismo color un 18% más oscuro (para el borde); con +10% lo aclara (para el hover).
  4. Si cambias $base, el borde y el hover se recalculan solos. Pruébalo y pasa el ratón por el recuadro de abajo.

3 · Lógica con @if / @else

Sirve para que un mismo mixin produzca CSS distinto según un parámetro: aquí, un tema claro u oscuro.

  1. Defines un mixin tema($modo) que recibe un parámetro.
  2. @if $modo == oscuro comprueba el valor recibido. Si se cumple, usa los estilos oscuros.
  3. @else cubre el resto de casos con los estilos claros.
  4. Al hacer @include tema(oscuro), SASS evalúa la condición durante la compilación y escribe solo la rama que toca. El CSS final no contiene ningún @if: ya está resuelto.

¿Se puede hacer lógica con CSS, o solo con SASS?

Es una distinción importante, porque ambos tienen "lógica" pero de naturaleza muy distinta. La clave es cuándo se resuelve.

SASS Lógica en compilación

Se evalúa una sola vez, antes de llegar al navegador. Genera CSS estático.

  • @if / @else: ramas condicionales.
  • @for, @each, @while: bucles que repiten reglas.
  • @function: funciones que devuelven valores calculados.
  • Operaciones con variables: $a * 2, comparaciones, etc.

Decide qué CSS se escribe. No reacciona a nada en tiempo de ejecución.

CSS Lógica en ejecución

El navegador la evalúa en vivo y reacciona al usuario, al tamaño de pantalla, al estado…

  • Variables nativas: var(--color) (cambiables con JS en caliente).
  • Cálculos vivos: calc(), clamp(), min(), max().
  • Condiciones de entorno: @media, @container, @supports.
  • Estados y selección: :hover, :has(), :nth-child().

Reacciona al contexto del usuario. No puede generar reglas en bucle.

En resumen: el @if/@for de SASS no existe en CSS nativo — esa lógica de "generar reglas" es exclusiva del preprocesador y se resuelve antes de publicar. Lo que CSS sí tiene es lógica reactiva (@media, calc(), :has(), variables con var()), que SASS no puede sustituir porque ocurre en el navegador. Por eso se complementan: SASS organiza y genera tu CSS; CSS reacciona en tiempo real. No eliges uno u otro para la lógica: usas cada uno para su tipo de lógica.
